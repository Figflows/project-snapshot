Getting started — Project Snapshot for Jira

Project Snapshot exports one Jira Cloud project — every issue, comment, worklog, change, link, attachment and the project's configuration — into ZIP files saved on your computer. Since version 1.1 it also exports any JQL query (everything, or attachments only) and shows you which projects have a recent snapshot and which have none. Since version 1.2 every full export includes a readable HTML archive, you can export only what changed since the last snapshot, and you can verify a downloaded ZIP against its manifest inside the app. Since version 1.3 a Jira admin can set a snapshot policy — "every project needs a snapshot no older than N days" — and the app checks it weekly and creates Jira reminder tasks for projects that fall behind. Every export happens in your browser. Nothing is uploaded anywhere.

What you need

  • Jira Cloud (Software, Work Management or Service Management).
  • Project admin permission on the project you want to export. The project page lives under Project settings, which Jira shows only to project admins. The Apps → Project Snapshot page is open to any Jira user, but it only shows projects you can browse and every export contains only what you can see. Changing the snapshot policy needs the Jira global permission Administer Jira.
  • A current desktop browser. Chrome and Edge are the browsers we test with; Firefox and Safari are not yet verified (the export uses ordinary file downloads, so they are expected to work, but we have not confirmed the multi-part flow there).
  • Free disk space roughly equal to the size of the project's attachments plus 10 %, and enough free memory for two ZIP parts at the chosen part size (see "Your first export", step 3).

Install

  1. Open the app's Marketplace page and click Get it now (or Try it free for sites with more than 10 users).
  2. A Jira site admin approves the installation. The app asks for three permissions: read:jira-work (read issues, projects and attachments), write:jira-work (used for one thing only: creating the "Snapshot due" reminder tasks when you switch the snapshot policy on and choose a reminder project — the app writes nothing else to Jira) and storage:app (the app's own small storage for the snapshot log and the policy described below). It asks for nothing else.
  3. That's it. Exports need no configuration. The snapshot policy is off until a Jira admin switches it on.

Your first export

  1. Open the project in Jira. Go to Project settings → Project Snapshot (bottom of the settings sidebar).
  2. The page shows the project key and the export options. (The issue count appears in the progress panel once the export starts; there is no count before that.)
  3. Choose a part size — 250, 500 or 1000 MB. A ZIP part is finished when it reaches this size or 60,000 files, whichever comes first. The browser keeps the part being built and the previous one (until the next is saved) in memory, plus the attachments being downloaded, so the tab needs roughly twice the part size free. If you're unsure, leave it at 500 MB. Use 250 MB on machines with less than 8 GB of RAM.
  4. Optionally enter a JQL filter to export only part of the project, for example fixVersion = "2.4". It is combined with project = KEY; a filter with unbalanced parentheses is rejected when you click Export. A filtered export is a partial snapshot (see step 11).
  5. Choose a mode: Everything (the default: per-issue JSON with comments, worklogs, change history, links, plus attachment files) or Attachments only (just the attachment files plus an issues.csv index — no JSON per issue).
  6. Leave Readable HTML archive (index.html + one page per issue) ticked unless you only want machine-readable files. It is not available in Attachments only mode.
  7. Click Export project.
  8. The first ZIP part is downloaded automatically, to wherever your browser puts downloads (if your browser is set to ask where to save each file, it asks once per part). Every further part pauses the export with a yellow Part N is ready — Save part N banner: click the button and the export continues. Browsers allow only one automatic download per click, which is why later parts need yours. If a part did not appear in your downloads, use Save part N again under the progress panel before the next part is ready.
  9. Watch the progress panel: issues processed, attachments downloaded, bytes written, current part and the list of saved parts. Leave the tab open and in the foreground until it says Done; if you try to close or reload it, the browser warns you.
  10. Read the Done line: "Done: X of Y issues, N attachments, P part(s)" — X is the number of issues actually written, Y the number processed — followed by the number of errors, if any. If errors are not zero, open errors.json in the last part to see what could not be fetched. A run that hits 25 failures in a row, or loses its session (HTTP 401/403 on a search), stops as Failed: the part in progress is discarded, parts already saved stay valid, and you run the export again after fixing the cause.
  11. When the export finishes, the app records it in the snapshot log (see below) and it appears in the Previous snapshots panel on this page. If it was a complete snapshot — mode Everything, no JQL filter, not incremental, on a licensed site, with zero errors — it becomes the project's current snapshot on the Coverage overview and the baseline for incremental exports. Any other export (Attachments only, filtered, incremental, sample mode, or with errors) is listed in the history marked "(partial)" and does not change Coverage. If the log write itself fails, a red banner says so; your ZIPs are unaffected.

Opening the HTML archive

  1. Unpack all parts of the snapshot into one folder (each part is a normal ZIP; index.html is in the last part, the issue pages are spread across the parts).
  2. Double-click index.html. It opens in any browser, offline: a list of all issues you can sort by clicking a column header and filter with the search box.
  3. Click an issue to open issues/<KEY>.html: fields (with the real names of custom fields), description, comments, worklogs, change history, links and links to the attachment files in attachments/.

The archive is static HTML. It loads nothing from the internet and contains no script apart from the inline sort and search on the index page. Do not open it from inside a ZIP viewer — unpack first, otherwise the links between the pages and to the attachments do not resolve.

Incremental exports

Once a project has at least one complete snapshot in the log, the export options show Incremental: only issues updated since the last snapshot with the date of that snapshot. Tick it and the export fetches only issues whose updated date is at or after that snapshot minus one hour (a safety margin so rounding can never skip an issue; an issue exported twice is harmless, a gap is not). The cut-off is written in the time zone of your Jira profile, which is how Jira reads JQL dates; if the app cannot read your time zone the margin is widened to 26 hours.

  • README.txt and manifest.json in the ZIP are marked INCREMENTAL with the cut-off time.
  • Keep incremental ZIPs together with the full snapshot they extend. An incremental export is a delta, not a complete record of the project. A typical routine is one full export, then one incremental export a month, all in the same folder.
  • Issues deleted in Jira since the last snapshot are not detected; they simply stay in the earlier snapshot.
  • Incremental is available on the project page only, not for Export by JQL.
  • An incremental export is itself a partial snapshot: it is listed as "(incremental)" in Previous snapshots, does not change the Coverage date and is never used as the baseline for the next incremental export — the baseline is always the last complete snapshot.
  • If you are not sure whether your set of ZIPs is complete, run a full export.

Previous snapshots

Below the export options, the project page lists every recorded snapshot of this project: date (with "(incremental)", "(filtered)" if a JQL filter was used, "(sample)" for sample mode and "(N errors)" if any), mode (Everything or Attachments only, with "(partial)" for every export that is not a complete snapshot), issues, attachments, size, parts and the first characters of the manifest's SHA-256. Two buttons:

  • Download evidence CSV saves the whole history as a CSV file (project, time, mode, counts, manifest hash, sample flag, JQL, errors, account ID of the person who ran it) — what an auditor asks for.
  • Delete log for this project removes all of this project's records from the snapshot log, immediately and permanently. The ZIPs on your disk are untouched; the project shows as "Never exported" on the Coverage overview until the next export.

The Project Snapshot page (Apps → Project Snapshot)

Version 1.1 added a page under the Apps menu; since 1.3 it has four tabs.

Coverage

Lists every project you can see with its most recent complete snapshot (Everything, no filter, not incremental, licensed, zero errors): date, issues, attachments and size. Partial exports never appear here. Pick a threshold — 30, 90, 180 or 365 days — and the page flags each project as Never exported, Stale (last snapshot older than the threshold) or fresh, with counts at the top and a filter to show only the flagged ones. The Open button takes you straight to that project's export page. Download coverage CSV saves the table (one row per project with its latest snapshot, status and age in days) for reporting.

The overview is built from the snapshot log, which started with version 1.1.0. Exports made with earlier versions are not in it, so a project you exported before upgrading shows as "Never exported" until you export it again.

Export by JQL

Paste any bounded JQL query (one that Jira can count — for example project in (FIN, OPS) AND created >= startOfMonth(); a trailing ORDER BY is ignored, issues are exported oldest first) and choose a mode:

  • Everything — the same output as a project export, for the matching issues: issues/<KEY>.json with all fields, comments, worklogs, changelog and links, attachment files, issues.csv, manifest.json and, if something failed, errors.json. Issues can come from several projects; project.json is omitted.
  • Attachments only — the attachment files under attachments/<KEY>/<id>-<filename> plus issues.csv (the same 16 columns as always: key, id, type, status, summary, assignee, reporter, priority, created, updated, resolved, labels, components, fix versions, parent, attachment count), manifest.json and, if something failed, errors.json. Useful for this month's invoices, last quarter's closed tickets for an auditor, or one client's deliverables for a hand-over.

Part size, progress, cancel, the HTML archive and verification work exactly as on the project page. The incremental option is not offered here, and JQL exports are not recorded in the snapshot log (they belong to no single project).

Verify a snapshot

Choose one or more downloaded ZIP parts with the file chooser. For each part the app reads the whole file into memory, unpacks it in your browser, reads its manifest.json and checks that every listed file is present, has the listed size and has the listed SHA-256 hash; files not in the manifest are reported as extra. The result is Verified, or Mismatch with a table of the files and the reason (missing, size, hash). Nothing is uploaded and no Jira request is made. Large parts take a while because every byte is hashed, and because the whole part is unpacked in memory a 1000 MB part needs a few GB of free memory in the browser — use the command line (below) for very large parts on small machines. Each part is checked against its own manifest, so verify every part of a multi-part snapshot.

Policy (since 1.3)

A snapshot policy says "every project needs a snapshot no older than N days", and the app enforces it for you: once a week it checks every project and reminds you about the ones that fall behind. Only Jira admins (global permission Administer Jira) can change it; everyone else sees whether a rule is in force.

  1. Tick Policy switched on (weekly check).
  2. Choose how old a snapshot may be: 30, 60, 90, 180 or 365 days.
  3. Leave Also flag projects that have never been exported ticked unless you only care about projects that already have a snapshot.
  4. Create reminder tasks in project — pick the project where the app should create its reminder tasks, typically a small admin or operations project. Leave it empty and the check only flags projects in Coverage, without creating anything.
  5. Tick Assign reminder tasks to me if the tasks should be assigned to you; Jira's normal notifications then tell you when one is created. The app itself never sends e-mail.
  6. Ignore these projects: keys of projects that should not be checked (sandboxes, archived projects), separated by commas or spaces; the list is tidied when you save. The reminder project itself is never checked.
  7. Save. Then click Run check now to run the same check immediately and see the summary: projects checked, projects behind the policy (with their keys), reminder tasks created, tasks skipped because one was still open, errors.

From then on the check runs once a week (only on sites with an active licence or the free tier). Only complete snapshots satisfy the policy — an attachments-only, filtered, incremental or sample export does not stop a reminder. For every project behind the policy it creates one Jira task in the reminder project — summary Snapshot due: KEY (name), label project-snapshot-reminder, a description with the reason ("never exported" or "last snapshot is 143 days old; the policy allows 90 days") and a link straight to that project's export page. At most 20 tasks per run; while a task for a project is still open no second one is created. Close the task once the snapshot is done — the next check sees it is closed and, when the project falls behind again, creates a fresh one.

Two things to know:

  • The weekly check runs without a signed-in user, and Jira shows an app only the projects it was explicitly granted. So the check uses the project list the app remembered the last time an admin opened the Coverage or Policy tab. Open one of them after creating new projects, and open one at least once before expecting the first weekly run to find anything.
  • The reminder project must have a Task-like issue type (the app uses the type named "Task" or, failing that, the project's first standard issue type) and the app must be allowed to create issues there. Projects with only sub-task or epic types, or with required custom fields on the create screen, cannot receive reminders; the last-run summary shows the error.

The snapshot log

After every finished project export the app stores one small record in Forge storage inside your Atlassian site: project id, key and name; mode; time; the Atlassian account ID of the person who ran it; counts (issues, attachments, bytes, parts, errors); the SHA-256 of the manifest; whether sample mode was on; the JQL used; the incremental cut-off, if any; and whether the export was a complete snapshot. Never issue content, comments or attachments. At most 50 records are kept per project; older ones are deleted automatically. Nobody outside your Atlassian site can read it, including us. Uninstalling the app removes it under Atlassian's Forge retention rules.

Since 1.3 the same storage also holds the snapshot policy settings, the summary of the last check, the app's own page ids (so reminder links point at the right page), the list of your projects (id, key and name, as seen by the admin who last opened Coverage or Policy) and the key of each reminder task the app created. Still metadata only.

What's in the ZIP

<KEY>-snapshot-<timestamp>-part01.zip
├── README.txt                what is inside and how to verify (every part)
├── project.json              project details and configuration:
│                             issue types, statuses, components, versions,
│                             roles, link types, field definitions (part 1)
├── index.html                readable archive: sortable, searchable list of all
│                             issues; opens offline in any browser (last part)
├── issues/
│   ├── <KEY>-1.json          one file per issue: all fields, comments,
│   ├── <KEY>-2.json          worklogs, changelog, links, attachment list
│   ├── <KEY>-1.html          the same issue as a readable page
│   └── …
├── attachments/
│   └── <KEY>-17/
│       └── 10023-design.pdf  original attachment bytes, named <id>-<filename>
├── issues.csv                spreadsheet-friendly index of all issues (last part)
├── errors.json               anything that could not be fetched — only present
│                             when something failed (last part)
└── manifest.json             every file in this part with size and SHA-256 hash
                              (every part; the last one also lists all parts)

The file name is <KEY>-snapshot-<UTC timestamp>-partNN.zip, for example DEMO-snapshot-20260929T140200Z-part01.zip. With multiple parts, README.txt and manifest.json are in every part, project.json in the first, and index.html, issues.csv and (if needed) errors.json in the last; each part's manifest covers that part's files. Issues and attachments are distributed across parts in order; a part holds at most 60,000 files. In Attachments only mode there is no index.html and no per-issue file. An incremental export has the same layout, and its README and manifest say INCREMENTAL.

Verifying an export later

In the app: Apps → Project Snapshot → Verify a snapshot, choose the ZIP part(s) with the file chooser. Everything is checked in your browser (see above).

On the command line, on macOS or Linux:

unzip -q KEY-snapshot-20260929T140200Z-part01.zip -d snapshot
cd snapshot
# compare hashes listed in manifest.json with the files on disk
jq -r '.files[] | "\(.sha256)  \(.path)"' manifest.json | sha256sum -c

On Windows, use Get-FileHash -Algorithm SHA256 <file> in PowerShell and compare with the value in manifest.json.

Licensing in one paragraph

Sites with 1–10 Jira users: free. Larger sites: 30-day free trial, then a subscription through Atlassian. Without a licence the app runs in sample mode — 25 issues, no attachments, and the Attachments only mode is disabled — so you can always check the output format. See the FAQ for details.

Troubleshooting — Project Snapshot for Jira

Start with errors.json in the last ZIP part, and with the progress panel. Almost every problem is explained by one of them.

The page is not in Project settings

  • You need project admin on that project. Ask a Jira admin to add you to the Administrators role, or run the export as someone who has it.
  • The app may not be installed, or a site admin has restricted which users can access it. Check Atlassian Administration → Apps → Manage apps.

Coverage shows "Never exported" for a project I exported before

The snapshot log that feeds the Coverage overview started with version 1.1.0. Exports made with 1.0.x were not recorded, so those projects show as never exported. Export the project once with 1.1 and it will be listed with that date. The ZIPs you made earlier are unaffected.

Coverage shows an older date than my last export

Coverage shows the last complete snapshot: mode Everything, no JQL filter, not incremental, licensed, zero errors. An attachments-only, filtered, incremental or sample export, or one that finished with errors, is listed in the project's Previous snapshots marked "(partial)" but does not move the Coverage date and does not satisfy the policy. Run a complete export.

The export said Done but a red banner says it could not be recorded

The ZIP files are complete and valid; only the write to the snapshot log failed (a temporary Forge problem, or you lost Browse permission on the project). Coverage and Previous snapshots do not show this export. Run it again later if you need it on record, or keep the manifest's SHA-256 shown under the progress panel as your evidence.

Coverage is missing a project

The overview lists only projects your account can browse. Ask a Jira admin for Browse Projects permission on the missing project, or ask someone who has it to open the overview.

The Incremental checkbox is not shown

It appears only when the snapshot log has at least one complete snapshot of this project (mode Everything, no filter, not incremental, licensed, zero errors; made with version 1.1 or later, and not deleted). Run one complete export; the next time the page opens, the option is there with that snapshot's date. It is offered on the project page only, not on Export by JQL.

An incremental export missed an issue

The incremental export fetches issues whose updated date is at or after the last complete snapshot's time minus one hour, with the cut-off written in your Jira profile's time zone (26 hours if the app cannot read it). An issue is not in it if:

  • it was not updated since then (it is in the earlier full snapshot — keep the ZIPs together);
  • it was deleted or moved out of the project (deletions are never detected; the old copy is in the earlier snapshot);
  • your account lost permission to see it (check errors.json and Jira's issue security);
  • it was updated between the last complete snapshot and a later partial export — the baseline is always the last complete snapshot, never a filtered, attachments-only, sample or incremental one, so nothing is skipped, but the same issue may appear in two incremental ZIPs.

If you are not sure your set of ZIPs is complete, run a full export. A full export is always the safe answer; incremental ones are an optimisation for large projects.

index.html shows nothing, or the links do not work

  • Open it after unpacking, not from inside the ZIP viewer or the browser's ZIP preview. Inside a ZIP the pages cannot reach each other or the attachments.
  • Unpack all parts into one folder. index.html is in the last part; the issue pages and attachments are spread across all parts. Missing pages or attachment links mean a part is missing from the folder.
  • If the list is empty but the page loads, the export was Attachments only (no HTML archive is produced in that mode) or the HTML option was unticked; the JSON files are still complete.
  • The search box needs JavaScript enabled for file:// pages; the page itself contains no external script.

Verify a snapshot says "Mismatch"

The result lists each file with a reason:

Reason Meaning What to do
missing A file listed in the manifest is not in the ZIP Re-download the part. If the download tool truncated it, the file size differs from the one on the export summary
size The file is there but its size differs Re-download; if it persists, the file was altered after export
hash Same size, different SHA-256 The content was changed after export — re-download; if the original download also says Mismatch, treat the archive as altered
extra A file in the ZIP is not in the manifest Something was added to the ZIP after export
"no manifest.json" The file is not a snapshot part, or it is a ZIP of the unpacked folder Verify the original downloaded part, not a re-zipped folder

The Verify tab reads the whole part into memory; if the browser tab runs out of memory on a very large part, verify it on the command line instead (see "Verifying an old archive"). A transfer error (partial download, a sync tool, an e-mail gateway) is the usual cause of a Mismatch. A Mismatch that survives a fresh download means the file on disk is not the one the app wrote, and the manifest hash recorded in the snapshot log (Previous snapshots, evidence CSV) is the reference. Each part is checked against its own manifest; verify every part.

I got a "Snapshot due" task I did not expect

A Jira admin on your site switched the snapshot policy on (Apps → Project Snapshot → Policy) and chose the project the task is in as the reminder project. The task means the project named in its summary has no snapshot younger than the rule allows, or was never exported. Its description says which and links to the export page.

  • If the reminder is right: run the export from the link and close the task.
  • If the project should not be checked: a Jira admin adds its key to Ignore these projects on the Policy tab and saves.
  • If nobody wants reminders: a Jira admin unticks Policy switched on (flags and tasks stop) or clears Create reminder tasks in project (flags in Coverage stay, no tasks). Existing tasks are not removed by the app; close or delete them like any other issue.
  • If you are the assignee and did not ask to be: the admin who saved the policy ticked Assign reminder tasks to me; untick it and save.

E-mails about these tasks come from Jira's notification scheme, not from the app.

The policy check found 0 projects

The weekly check runs without a signed-in user, and Jira shows an app only the projects it was explicitly granted — usually none. The check therefore uses the project list the app remembered the last time someone opened the Coverage or Policy tab. If nobody has opened either since the app was installed (or the list was empty), the check has nothing to compare.

Open Apps → Project Snapshot → Coverage or Policy once as a Jira administrator (only administrators can update the remembered project list), then click Run check now. The summary should now show the number of projects checked. Repeat after creating new projects; the list is refreshed every time one of those tabs is opened.

No reminder tasks were created

Check the last-run summary on the Policy tab, top to bottom:

Summary says Cause What to do
policy switched off The check ran but the policy is off Tick Policy switched on, save, run again
0 projects checked No remembered project list See the previous entry
N behind the policy, 0 tasks created, no reminder project Create reminder tasks in project is empty; the check flags only Choose a reminder project and save
N behind, 0 created, N already open A task for each project is still open Nothing to do — close the tasks when the snapshots are done
error "Reminder project X not readable: HTTP 404" The app cannot see the reminder project (it was deleted, renamed, or the app's access to it was restricted) Choose another project
error "has no usable issue type" The reminder project has only sub-task or epic types Use a project with a standard issue type such as Task
error "HTTP 400 …" naming a field The create screen of the reminder project's Task type has required custom fields the app cannot fill Make those fields optional, or pick a plainer project
error "HTTP 403" The app is not allowed to create issues in that project (permission scheme: Create Issues must include the app, or atlassian-addons-project-access) Ask a Jira admin to check the permission scheme of the reminder project

The reminder project needs a Task-like issue type: the app looks for an issue type named "Task" (also its German, French, Spanish and Swedish names) and otherwise takes the project's first standard type. The reminder project itself is never checked and never gets a reminder. Remember the check creates at most 20 tasks per run; on a site with more projects behind the rule, the rest follow in later runs. Projects deleted in Jira stay in the remembered list until a Jira admin opens Coverage or Policy again, so a deleted project can receive one more reminder whose export link no longer works — open one of those tabs after deleting projects.

The same project got a second reminder task

The app never creates a task for a project while an earlier one is open (any status outside the Done category), so a second task means the first was closed and the project was still behind the policy at the next check. Export the project and close the task; nothing more is created until the snapshot is older than the rule again. If you see two open tasks for one project, one was created outside the app (the app checks by label and summary text in the reminder project) — close the extra one and e-mail us the two keys if it repeats.

The Policy tab says "Only Jira administrators can view or change the snapshot policy"

Changing the policy and clicking Run check now require the Jira global permission Administer Jira; the app checks this on the server. Ask a Jira admin to set the policy, or to add you to a group with that permission. Coverage, Export by JQL and Verify are unaffected.

I deleted a project's log by mistake

The deletion is immediate and cannot be undone by the app. The ZIPs on disk are unaffected. Run a new export to record the project again; for the earlier dates, keep the earlier manifest.json files (they carry the export timestamp and app version).

"Attachments only" is greyed out

Attachments only needs a licence; in sample mode (no active licence) it is disabled because sample mode skips attachments. See the next entry.

Export by JQL refuses to start

The query must be bounded — Jira must be able to count it. Queries such as ORDER BY created on their own or ones that produce a JQL error are rejected. Test the JQL in the issue navigator first, then paste it. Very large results are fine but take time; consider splitting by date.

"Unlicensed — sample mode" banner

  • Jira reports no active licence for the app on this site. Check Atlassian Administration → Billing → Manage subscriptions. After activating, reload the page.
  • If Billing says active and the banner stays: sign out and in again; if it persists, e-mail andre@figflows.com with screenshots of both.

Export stops or the browser tab crashes

Symptoms: "Aw, Snap!", a frozen tab, or the progress panel stops advancing.

  1. Reduce the part size to 250 MB. The browser holds the part being built and the previous one (until you have saved the next) in memory, plus up to three attachments being downloaded.
  2. Use Chrome or Edge (the browsers we test with). Close other tabs and heavy applications.
  3. Keep the tab in the foreground. Some browsers throttle background tabs heavily.
  4. Split the export with JQL by date, e.g. created < 2025-01-01 and created >= 2025-01-01.
  5. Check disk space: each part is written as it completes.

Parts already saved before the crash are valid; you can export the remaining issues with a JQL filter such as key > KEY-1234 (use the last key in the saved part's manifest). Note that index.html, issues.csv and the parts list are only written by a run that finishes, so the second run produces its own index for its own issues; there is no resume that stitches both runs together.

The export stopped with "Failed: Stopped after 25 consecutive failures"

Twenty-five items in a row could not be fetched, which almost always means the session expired (HTTP 401), Jira is refusing the account (403) or the site is down (5xx). The part in progress was discarded; parts already saved are valid. Reload Jira, sign in again, and run the export again. The same stop happens immediately when a search page itself returns 401 or 403.

The export stopped with "Failed: The JQL filter has unbalanced parentheses or quotes"

The optional JQL filter is wrapped in parentheses and combined with project = KEY; a filter with an unmatched (, ), " or ' is refused before any request is made. Fix the filter and try again.

Entries in errors.json

Each entry has scope (issue, comments, worklogs, changelog, attachment, config or search), key (issue key or, for config, the section name), attachmentId where relevant, status (HTTP status, when there was one) and message. Note that the top level of manifest.json also has a field called scope; there it describes what was exported (project or JQL), not an error category. The file exists only when at least one item failed.

Status Meaning What to do
401 Session expired during a long export Reload Jira, sign in, run again
403 Your account can see the issue but not this item (issue security, restricted comment, portal-only attachment) Get access granted or run as a user who has it; re-run
404 Item no longer exists in Jira (deleted after the issue list was fetched, or moved) Check in Jira; if gone there, nothing to recover
429 Jira rate limit; the app backed off and retried but the item still failed Run again later; failed items will be fetched. Very busy sites: use JQL splits and export off-peak
5xx Jira-side error Retry later; if persistent, check https://status.atlassian.com
network Connection dropped Check your connection; re-run

A re-run after fixing the cause fetches the previously failed items. Earlier parts remain valid.

Attachment file names look odd

Files are saved as <attachmentId>-<originalName> so that two attachments with the same name on one issue never collide. Characters that are illegal in file names on Windows or macOS are replaced with _. The original name is preserved in the issue JSON.

The issue total in the progress panel differs from the number of issues exported

  • The total is Jira's approximate count, taken when the export starts; it can lag behind recent changes. The Done line reports "X of Y issues": X were written, Y were processed.
  • Issues created or deleted during the export may be missed or 404'd; both cases appear in errors.json if the app noticed.
  • In sample mode the export is capped at the first 25 issues returned.

Custom field values look like IDs

That is how Jira returns them. project.json contains the field definitions (ID → name, type, allowed values where Jira provides them). Map them when you process the data.

The browser asks where to save every part (or doesn't ask at all)

Every part is an ordinary browser download; the app cannot pick a folder for you (the File System Access API is not available inside the Jira page). Where the file goes, and whether you are asked, is your browser's download setting ("Ask where to save each file before downloading"). The first part starts by itself; every further part waits for you to click Save part N, so you are never asked for several files at once. If the browser asks whether to allow multiple downloads from the site, allow it.

The export is slow

  • Attachments dominate. Speed is bounded by your connection and Jira's per-user rate limits.
  • Run exports outside busy hours, avoid running other API-heavy integrations at the same time, and keep the tab in the foreground.
  • Use JQL to export only what you need.

Verifying an old archive

In the app: Apps → Project Snapshot → Verify a snapshot, choose the ZIP part(s) with the file chooser. On the command line:

jq -r '.files[] | "\(.sha256)  \(.path)"' manifest.json | sha256sum -c

Any line other than OK means the file has changed or is missing since export.

Still stuck

E-mail andre@figflows.com with: site URL, project key (or the JQL used), browser and version, OS, a screenshot of the progress panel, and errors.json. Do not send the export itself or issue contents.

The unzip command complains about a filename

Attachment names with emoji or other non-Latin characters are stored in the ZIP as UTF-8. The old unzip tool bundled with macOS sometimes prints a write error for such names. Open the ZIP by double-clicking it in Finder, or use ditto -x -k file.zip folder on macOS, tar -xf file.zip, 7-Zip on Windows, or Python's zipfile module. The file contents and hashes are unaffected.

Only the first ZIP part was downloaded

Browsers allow one automatic download per click. For that reason the app pauses after each further part and shows a Save part N button; click it and the export continues. If a part still does not appear in your downloads folder, use Save part N again under the progress panel while the page is still open. Do not close or reload the tab before the last part is saved.

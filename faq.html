FAQ — Project Snapshot for Jira

General

What does the app do, in one sentence? It exports one Jira Cloud project completely — issues, comments, worklogs, history, links, attachments and configuration — or any JQL query, into ZIP files on your computer with a readable HTML archive inside, lets you verify them later, keeps an overview of which projects have a recent snapshot, and reminds you with a Jira task when a project falls behind your snapshot policy.

Where does the data go? From Jira, through your browser, to your disk. The app has no server of its own and no connection to anything but Atlassian. The only thing it stores is a small snapshot log inside your Atlassian site (see "What does the app store?"). We (the vendor) never see your data.

What does the app store? One small record per finished project export, in Atlassian's Forge storage inside your own site: project id, key and name; mode (everything or attachments only); timestamp; the Atlassian account ID of the person who ran it; counts (issues, attachments, bytes, ZIP parts, errors); the SHA-256 of the manifest; whether sample mode was on; the JQL used; the incremental cut-off, if any; and whether the export was a complete snapshot. Exports by JQL from the Apps page are not recorded. Never issue content, comments or attachments. At most 50 records per project are kept; older ones are deleted automatically. It stays in your Atlassian site's region, we cannot read it, and Atlassian deletes it when you uninstall the app.

Since 1.3 the same storage also holds the snapshot policy (the rule, the reminder project, the optional assignee's account ID, the ignored project keys, the summary of the last check), the list of your projects (id, key, name — remembered when a Jira admin opens Coverage or Policy, because the weekly check runs without a user) and the key of each reminder task the app created. Names and keys of projects are the only new data; still no issue content.

What is a complete snapshot? An export in mode Everything, without a JQL filter, not incremental, made on a licensed site, that finished with zero errors. Only complete snapshots count: they set the date on the Coverage overview, satisfy the snapshot policy and serve as the baseline for incremental exports. Every other export — Attachments only, filtered, incremental, sample mode, or with errors — is still recorded in the project's Previous snapshots, marked "(partial)", but never makes a project look covered. So a quick attachments-only export does not silence a "Snapshot due" reminder.

What is the snapshot policy? A rule — "every project needs a complete snapshot no older than 30, 60, 90, 180 or 365 days" — that a Jira admin sets on Apps → Project Snapshot → Policy. Once a week the app checks every project against it, flags the ones behind in Coverage and, if you chose a reminder project, creates one Jira task per project: Snapshot due: KEY (name), labelled project-snapshot-reminder, with the reason and a link to that project's export page, optionally assigned to you. At most 20 tasks per run, never a second one while the first is still open. Leave the reminder project empty and you get flags only. Run check now runs the same check immediately.

Why did I get a "Snapshot due" task? Because a Jira admin on your site switched the snapshot policy on, chose the project the task is in as the reminder project, and the project named in the task has no snapshot younger than the rule allows (or was never exported, if that option is ticked). The description says which, and links to the export page. Run a complete export (mode Everything, no filter, not incremental — an incremental or attachments-only export does not satisfy the policy) and close the task. If nobody wanted these tasks, a Jira admin can switch the policy off or clear the reminder project on the Policy tab; existing tasks stay until you close or delete them.

How often does the check run, and can I trigger it? Once a week, automatically, on sites with an active licence or the free tier (not in sample mode). A Jira admin can also click Run check now on the Policy tab at any time; it does exactly what the weekly run does and shows the summary.

The check says it found 0 projects. Why? The weekly check runs without a signed-in user, and Jira shows an app only the projects it was explicitly given access to — often none. So the check uses the project list the app remembered the last time someone opened the Coverage or Policy tab. Open one of them once as a Jira administrator who can see the projects that matter (only a Jira admin's visit updates the list) and run the check again. Do the same after creating new projects.

Does closing the reminder task stop new ones? Closing it (any status in the Done category) tells the next check that the reminder was handled. If the project is still behind the policy at the next weekly run — because no export was made — a new task is created. If you exported the project, it is no longer behind and nothing is created. Reopening a task instead of closing it also prevents duplicates: the app never creates a second task for a project while one is open.

Does the app send e-mail? No. It cannot; it has no mail capability and no connection outside Atlassian. If you receive an e-mail about a Snapshot due task, it comes from Jira's own notification scheme, because you are the assignee or watch the reminder project. Adjust it in Jira's notification settings as for any other issue.

Can I delete the snapshot log? Yes, if you have the Jira permission Administer Projects on that project (or Administer Jira); the app checks this with Jira before deleting and refuses otherwise. On a project's page, Previous snapshots → Delete log for this project removes all of that project's records immediately. Your ZIPs are unaffected; the project shows as "Never exported" until the next export. Uninstalling the app removes the whole log.

What is the evidence CSV? A CSV download of a project's snapshot history (time, mode, counts, manifest hash and — for Jira administrators — the JQL and who ran it), from the Previous snapshots panel. The Coverage overview has a similar Download coverage CSV with one row per project. Both are built in your browser from the snapshot log and are meant for auditors and reports.

How do I find projects that were never exported? Open Apps → Project Snapshot → Coverage. Every project you can see is listed with its last complete snapshot; choose a threshold (30, 90, 180 or 365 days) and the page flags projects as Never exported or Stale, with counts and a filter. Click Open to go to the project's export page. The log started with version 1.1.0, so projects exported with 1.0 show as never exported until you export them again.

Can I export something that is not one project? Yes. Apps → Project Snapshot → Export by JQL exports any bounded JQL query — across projects if you like — either as Everything (full per-issue JSON plus attachment files) or Attachments only.

What is "Attachments only"? A mode, on both pages, that fetches just the attachment files plus an issues.csv index and manifest.json (and errors.json if something failed). No per-issue JSON. It is a partial snapshot: it does not count as coverage. Typical uses: this month's invoices, evidence for an auditor, deliverables for a client. It is disabled in sample mode.

Why does this exist? Jira has export. Jira's CSV export stops at 10,000 issues (Jira now also calls them work items) and gives you links to attachments rather than the files. Jira's site-wide export covers the whole site, and with attachments included Atlassian allows one every 48 hours. Neither gives you one project, complete, with the actual files and the change history. Project archiving is only on Premium and Enterprise plans.

Can I restore from a snapshot? No. A snapshot is an archive, not a backup with restore. The app never writes issue data back to Jira (the only thing it ever creates is a reminder task, and only if you switch the policy on). What you get is a complete, verifiable, readable copy on your own disk that outlives the project — for hand-over, audit, legal hold or reference. If you need automated backup with restore into Jira, look at the dedicated backup services on the Marketplace; they cost more because they store your data on their servers and can put it back.

What is the readable HTML archive? Every full export contains index.html — a sortable, searchable list of all issues — and issues/<KEY>.html, one page per issue with its fields (custom fields under their real names), description, comments, worklogs, change history, links and links to the attachment files. Unpack all parts into one folder and open index.html in any browser, offline. No Jira account and no tool needed — a client, a lawyer or a former colleague can read it. It can be switched off in the export options, and it is not produced in Attachments only mode.

Is the HTML archive safe to open? Yes. It is static HTML generated by the app. All issue content is escaped, so text from comments or descriptions is displayed, never executed. The pages load no external resources — no fonts, images, styles or scripts from the internet — so opening them makes no network request. The only script is the inline sort and search on index.html. Links in issue text are kept only if they are http(s) or mailto links. As with the JSON files, the archive contains the personal data that was in the issues, so store and share it accordingly.

What is an incremental export? On the project page, once the project has a complete snapshot in the log, you can tick Incremental: only issues updated since the last snapshot. The export then fetches only issues updated at or after that snapshot minus one hour (a safety margin; the cut-off is expressed in your Jira profile's time zone, and the margin grows to 26 hours if the app cannot read it). It is meant for a monthly routine on big projects: one complete export, then small incremental ones. The ZIP's README and manifest are marked INCREMENTAL. Keep incremental ZIPs together with the complete snapshot they extend — on their own they are not a complete record, they are listed as "(incremental)" in Previous snapshots, and the baseline for the next incremental export stays the last complete snapshot.

How do I check that a downloaded snapshot is intact? Open Apps → Project Snapshot → Verify a snapshot and choose the ZIP part with the file chooser. The app reads the whole part into memory and unpacks it in your browser and checks every file's presence, size and SHA-256 hash against the part's manifest.json, then reports Verified or Mismatch with the reason per file. Nothing is uploaded. You can also do it on the command line — see the getting-started guide.

Does it work with team-managed and company-managed projects? Yes. Configuration details differ (team-managed projects have their own issue types and fields), and project.json reflects what Jira returns for that project type.

Does it work with Jira Service Management? Yes, for the issue and attachment data your account can see. Customer-portal-only content that your account cannot read will be listed in errors.json.

Permissions and security

What permission does it need? Three scopes. read:jira-work for everything the exports read. write:jira-work, added in 1.3, for exactly one thing: creating the "Snapshot due" reminder tasks when a Jira admin has switched the policy on and chosen a reminder project — the app never edits, transitions, comments on or deletes anything, and with the policy off it writes nothing. storage:app for the app's own snapshot log and policy settings. No user directory access.

What exactly does write:jira-work let the app do? Create issues. The app uses it in one function only — the weekly policy check — to create a task in the reminder project you chose, with a fixed summary, a fixed label and a description containing the reason and a link. The weekly check runs as the app because it happens without anyone signed in; Run check now runs the same check as the Jira administrator who clicked it. It is never used by an export, by Coverage, by Verify or by the snapshot log. If you never switch the policy on, the scope is never exercised.

Can someone use it to export data they shouldn't see? No. Every export request is made as the signed-in user, and Jira enforces that user's permissions. The export contains exactly what that user could see by clicking through Jira. The policy check (as the app on its weekly schedule, as the clicking admin for Run check now) reads no issue content at all; it compares the snapshot log with the project list.

Who can open the pages? The project page: project admins, because it sits under Project settings. The Apps → Project Snapshot page: any Jira user, but it lists only projects they can browse (checked by the app's backend, not just hidden in the page), and any export contains only what they can see. Snapshot history: anyone who can browse a project sees its export dates, mode and counts; who ran an export and the JQL used are shown only to Jira administrators. Deleting a project's log: Administer Projects on that project, or Administer Jira. The Policy tab can be changed, the check run by hand (this also needs an active licence) and the remembered project list refreshed only by users with the Jira global permission Administer Jira; the app checks all of this server-side. Other users see only the rule itself (on/off, allowed age, whether never-exported projects count) — not the reminder project, the assignee, the ignored projects or the last-run summary.

I cannot delete the log or change the policy. Why? Because your Jira account lacks the permission the action needs, and the app checks it with Jira on every request. Deleting a project's log needs Administer Projects on that project (a project admin normally has it) or Administer Jira. Changing the policy, running the check by hand, and refreshing the project list the weekly check uses, need Administer Jira. Running the check by hand also needs an active licence. Ask a Jira admin to grant the permission or to do it for you; the app has no override of its own.

What is the worst a wrongly configured policy can do? Create unwanted reminder tasks — at most 20 per weekly run, clearly labelled project-snapshot-reminder, in the one project chosen as the reminder project. Nothing is changed or deleted. Switch the policy off or clear the reminder project and it stops; delete the tasks like any other issue.

Does verifying a snapshot upload my ZIP? No. The Verify tab reads the file you select in your browser, hashes it there and discards it. It makes no request to Atlassian or to us.

Is it "Runs on Atlassian"? Yes. The app has no external servers and no egress; its only storage is Atlassian's own Forge storage, which is what that Marketplace badge allows. Atlassian applies the badge automatically.

Do you have a DPA? Not needed for the app: we do not receive any of your data, so we are not a processor of it. Our privacy policy covers the only data we do process — support e-mails. Details: https://figflows.github.io/project-snapshot/data-handling.html.

Output

What format is the output? Plain JSON (one file per issue plus project.json), a CSV index, the original attachment files, manifest.json with SHA-256 hashes, errors.json when something failed — plus, in full exports, a readable HTML archive (index.html and one page per issue). No proprietary format.

What exactly is in each issue file? All fields returned by Jira's issue API (system and custom, with their raw values), all comments, all worklogs, the full changelog, issue links, and the list of attachments with their IDs so they can be matched to files in attachments/.

Why are the fields so verbose? Because we store what Jira returns, unmodified. Human-readable names of custom fields are in project.json under field definitions, so you can map customfield_10042 to "Story points" later. The HTML pages already show the real names.

Can I open it in Excel? issues.csv is meant for that: one row per issue with the common fields. The full detail is in the JSON files.

What is manifest.json for? It lists every file in the ZIP with its size and SHA-256 hash. Anyone can later verify that nothing has been changed — with the app's Verify a snapshot tab or any hashing tool. Useful for audits, legal hold and hand-overs.

What is errors.json for? It records everything the app tried to fetch and could not, with the HTTP status and a message. It is only written when there was at least one error, so an export whose last part has no errors.json (and whose Done line reports no errors) is complete. Never assume completeness without checking.

Size and performance

How big can a project be? There is no hard limit in the app, but there is in your browser's memory. Exports are split into parts of 250, 500 or 1000 MB (or 60,000 files, whichever comes first); the browser keeps the part being built and the previous one (until the next is ready) in memory, plus the attachments being downloaded, so with the 1000 MB setting a tab needs well over 2 GB free. The largest export we have run is 2,122 issues with 543 MB of attachments into two parts; bigger projects are expected to work part by part, one click per part, but have not been tested. A run that fails is not resumable (see Troubleshooting), so for very large projects split by date with a JQL filter and keep the tab in the foreground.

How long does it take? Roughly: issues at a few hundred per minute; attachments at whatever your connection and Jira's rate limits allow. A 5,000-issue project with 2 GB of attachments is typically well under an hour. Jira rate limiting (HTTP 429) slows things down; the app backs off and retries.

Can I export only part of a project? Yes — enter a JQL filter (the result is recorded as a partial snapshot). For queries that span projects, use Apps → Project Snapshot → Export by JQL. For "only what changed since last time", tick Incremental.

Can I cancel? Yes. Parts already written stay on disk and are valid on their own. The part being built is discarded.

Can I close the tab and come back? No. The export runs in the tab; closing or reloading it stops the export (the browser warns you first). Parts already saved are fine.

Which browsers are supported? We test with current desktop Chrome and Edge. Firefox and Safari are not yet verified: the export uses ordinary file downloads, so they should work, but we have not confirmed the multi-part "Save part N" flow there. Mobile browsers are not supported.

Licensing

Is there a free version? Yes. Sites with 1–10 Jira users use the full app for free.

What does the trial include? Everything, for 30 days. Atlassian runs the trial; it converts to a paid subscription unless you cancel under Atlassian Administration → Billing.

What happens without a licence? The app runs in sample mode: the first 25 issues the search returns, no attachments, same file structure including the HTML archive; Attachments only is disabled. Enough to check the output format. Sample exports are recorded as partial and do not count as coverage. Nothing is locked or deleted.

How is the price calculated? Per Jira user on your site, on Atlassian's user tiers. Annual is 10 × monthly. The current table is on the Marketplace listing.

How do I get a refund? Through Atlassian: https://support.atlassian.com/contact/ → Billing. Atlassian handles all payments for Marketplace apps; we never see payment details.

Data handling and security — Project Snapshot for Jira

This document is the app's security policy for the Marketplace "Security policy" link and for customer security reviews. Publish it at https://figflows.github.io/project-snapshot/data-handling.html.

Every API call is made by the Forge Custom UI bridge (requestJira) as the signed-in user. Atlassian enforces the user's permissions on every call. The app cannot see anything the user cannot.

Two things added in 1.2 happen entirely in the browser and add no arrow to the diagram: the readable HTML archive (index.html, issues/<KEY>.html) is rendered from the issue data already in memory while the ZIP is built; and the Verify a snapshot tab reads a ZIP part the user selects from their own disk, hashes every file in memory and compares it with the part's manifest.json. Verification uploads nothing and makes no Jira request. The only new server-side operation is deleteProjectLog, which removes a project's snapshot-log records from Forge storage when a user with the Jira permission Administer Projects on that project (or Administer Jira) asks for it; the resolver verifies that permission with Jira before deleting.

Version 1.3 adds the snapshot policy and, with it, the app's only write to Jira. Two more arrows, both inside Atlassian:

The scheduled function runs without a user, so it calls Jira as the app (asApp()): it reads serverInfo and the reminder project's issue types, checks whether an earlier reminder is still open (GET issue/{key}, POST search/jql on the label), and creates at most 20 tasks per run. It never reads issue content of the projects it checks; it only compares the snapshot log with the remembered project list. No e-mail is sent by the app; Jira's own notifications inform the assignee. With the policy off, or with no reminder project chosen, the function writes nothing.

The ZIP files may therefore contain personal data of the customer's users. Once written, they are ordinary files on the user's device under the customer's control.

3. Storage

  • App storage: metadata only. Forge Key-Value Storage (storage:app scope), Atlassian-hosted. The snapshot log uses two key families: latest:<projectId> (most recent record, for the coverage overview) and snap:<projectId>:<timestamp> (history). After each write the app trims history to the newest 50 records per project. The account id and timestamp are set server-side by the resolver from the Forge context; the browser cannot forge them. Each record also carries a server-computed complete flag (full mode, licensed, no JQL filter, not incremental, zero errors); only complete snapshots are written to latest:, so the coverage overview, the policy and the incremental baseline never rely on a partial export. Since 1.2 the resolver also serves history (the records of one project, newest first) and deleteProjectLog (removes all records of one project when a user with Administer Projects on it, or Administer Jira, asks). Since 1.3 there are five more keys: policy (the snapshot policy settings, validated server-side: only the allowed day values, project keys matching Jira's key pattern, at most 500 excluded keys), policy:lastRun (summary of the last check; a refused reminder create is recorded as the project key, the HTTP status and at most 160 characters of Jira's error message — visible to Jira administrators only), policy:install (the app and environment ids, stored when an administrator saves the policy, so that reminder links created by the weekly run point at the right page), projects (the remembered project list — id, key, name, type; at most 1,000 entries, names cut to 80 characters; written only by Jira administrators and overwritten each time one opens the Coverage or Policy page) and reminder:<projectId> (the issue key of the reminder task created for that project). No issue content in any of them. No entity properties, no SQL, no external database. Every resolver checks the calling user's Jira permissions server-side (mypermissions, as the user) before it reads, writes or deletes: Browse Projects on the project to log a snapshot or read its records; Administer Projects on the project or Administer Jira to delete them; Administer Jira to store the project list, change the policy or run the check. Reads of the log are filtered to the projects the user can browse, and the exporter's account id and the JQL are returned only to Jira administrators.
  • Browser storage: none. The app does not use cookies, localStorage, sessionStorage, IndexedDB or the Cache API.
  • Memory: issue JSON and attachment bytes are held in browser memory only for as long as it takes to compress them into the current ZIP part (at most three attachments are being downloaded at once). Each part is released after it is written; only the most recently written part is kept until the next one is ready (so it can be saved again if the download did not appear), so peak memory is about two parts plus the attachments in flight. Cancelling, leaving the page or closing the tab aborts the export and discards everything not yet written. Chrome, Edge and Firefox show a leave-page warning while an export is running; Safari does not show this warning for apps embedded in Jira.
  • Logs: the app writes no log output. Neither the resolver nor the scheduled policy function logs payloads. Forge platform logs (invocation metadata) are Atlassian's and contain no issue content, because no issue content ever reaches the app's backend.

4. Encryption

  • In transit: all traffic is between the user's browser and Atlassian, over Atlassian's TLS. The app adds no connections of its own.
  • At rest: the snapshot log is in Forge-hosted storage, encrypted at rest by Atlassian. Files on the user's disk inherit whatever disk encryption the user has. We recommend full-disk encryption and encrypting ZIPs before they leave the organisation.
  • Integrity: manifest.json records a SHA-256 hash of every file so tampering or corruption can be detected later. Since 1.2 the Verify a snapshot tab does this check in the browser: presence, size and SHA-256 of every file in a part against that part's manifest, reported as Verified or Mismatch with the reason per file.
  • HTML archive rendering: the readable archive is static HTML generated by the app with strict escaping of all issue content; the only script is the inline sort/search on index.html; there are no external resources (no fonts, images, stylesheets or scripts fetched from anywhere); links are limited to http(s) and mailto targets and to the archive's own files. Opening it makes no network request.
  • CSV files: in issues.csv, the evidence CSV and the coverage CSV, any cell that begins with =, +, -, @, a tab or a carriage return is prefixed with an apostrophe so that spreadsheets do not execute it as a formula (OWASP CSV-injection guidance).
  • ZIP entry names: attachment filenames are sanitised before they become ZIP paths — path separators, control characters and invisible Unicode format and bidirectional-override characters are removed, ./.. are replaced, length is capped — and each file is prefixed with its attachment id under attachments/<KEY>/.

5. Retention and deletion

  • The app retains only the snapshot log, in Forge-hosted storage. At most 50 records per project; older ones are deleted automatically at the next export.
  • On uninstall, Atlassian soft-deletes the app's Forge-hosted storage and then destroys it under Atlassian's standard retention schedule; a customer can ask Atlassian to relink the data to a new installation within 21 days (Forge "Data lifecycle for Forge-hosted storage"). The vendor holds no copy and cannot read the log. Uninstalling removes the app pages immediately.
  • The log started with version 1.1.0; exports made with 1.0.x are not in it. Since 1.2.0 a user with the Jira permission Administer Projects on a project (or the global permission Administer Jira) can delete that project's log (all its records, immediately) with Delete log for this project on the project page; the resolver verifies that permission with Jira, carries out the deletion in Forge storage, and it cannot be undone.
  • Since 1.3.0 the policy settings persist until a Jira admin changes them (switching the policy off keeps the settings but stops all checks and writes); the remembered project list is replaced on every visit by a Jira administrator to the Coverage or Policy page; the reminder key for a project is replaced when a new reminder is created for it. All of it is removed with the app's storage on uninstall.
  • Reminder tasks created in Jira are ordinary issues in the customer's own project. The app never deletes or edits them; the customer closes or deletes them like any other issue. Uninstalling the app leaves them in place.
  • Exported files are retained by the customer for as long as the customer decides. Deleting them is an ordinary file deletion on the customer's device.
  • Support correspondence: see privacy-policy.md (24 months, bookkeeping records 7 years).

6. Access control

  • Scopes: read:jira-work ("Read Jira project and issue data, search for issues and objects associated with issues like attachments and worklogs"), write:jira-work (since 1.3; used for exactly one operation — creating the "Snapshot due" reminder tasks of the snapshot policy, only while the policy is on and a reminder project is set; no other write) and storage:app (Forge-hosted storage: snapshot log, policy, project list, reminder keys). No read:jira-user. No admin scope.
  • Who can open the pages: the project page is under Project settings, which Jira shows only to project admins. The global page (Apps → Project Snapshot) is reachable by every Jira user; its Coverage overview and the snapshot-log resolvers return only projects the calling user can browse (checked server-side, as that user), and every export still runs as the user — Jira itself refuses issues and attachments the user may not see, so the app performs no separate pre-check before an export.
  • Who can delete a project's log: users with the Jira permission Administer Projects on that project, or Administer Jira; the resolver checks mypermissions?projectId=…&permissions=ADMINISTER_PROJECTS as the calling user and refuses otherwise.
  • Who sees what in the log: anyone who can browse a project sees its export dates, mode and counts; the exporter's account id and the JQL used are returned only to Jira administrators.
  • Who can change the policy: only users with the Jira global permission Administer Jira. The resolver checks mypermissions?permissions=ADMINISTER as the calling user before saving the policy or running the check by hand; other users receive only the rule itself (on/off, allowed age, whether never-exported projects count), not the reminder project, the assignee, the ignored projects or the last-run summary. Running the check by hand additionally requires an active licence. The project list the weekly check uses is written only when a Jira administrator opens the Coverage or Policy page (at most 1,000 projects: id, key, name cut to 80 characters, type); other users' visits do not change it.
  • Runs as user / as app: every export call uses the user's own identity. asApp() is used only by the policy check (which runs on a schedule, without a user) and only for: creating a reminder task in the chosen project, reading the status of a task it created earlier, searching that project by the reminder label, reading serverInfo and the reminder project's issue types. The app identity never reads issue content of the projects being checked; it works from the snapshot log and the remembered project list. The resolver's own Jira calls are all made as the calling user and are read-only: mypermissions (Administer Jira, Browse Projects, Administer Projects) and project/search to list the projects that user can browse.
  • Licence: sample-mode limits (25 issues, no attachments) are enforced in the browser only; every export call still runs with the user's own Jira permissions, so bypassing them exposes nothing the user could not already read in Jira. The policy check runs only on licensed sites: the scheduled trigger is filtered by licence and the manual run checks the licence in the resolver.
  • No secrets: the app holds no API keys, tokens, passwords or shared secrets. It never sees Atlassian PATs.

7. Sub-processors

For app data: none. No third party receives any customer data through the app, because the app transmits data only between Atlassian and the user's own device, and the snapshot log is held by Atlassian itself (Forge-hosted storage), which is already covered by the customer's agreement with Atlassian.

For support: our e-mail provider, Microsoft 365 (Microsoft Ireland Operations Ltd), processes support correspondence (see privacy-policy.md).

Statement for customers asking for a DPA: "Project Snapshot for Jira does not transmit, store or otherwise process Customer Data outside the Customer's Atlassian site and the end user's own browser and device. FigFlows AB does not receive Customer Data through the app and therefore does not act as a processor of it under GDPR Article 28. A DPA is not required for the app. Atlassian's own DPA governs the Jira platform."

8. Egress and remotes

  • Egress permissions in manifest: none. No permissions.external entries.
  • Remotes: none.
  • Content Security Policy: Forge's default Custom UI CSP; no additional fetch, images, scripts or styles domains.
  • Runs on Atlassian: eligible (no external domains, no remotes, no Connect modules, no providers, no dynamic web triggers; Forge-hosted storage and a Forge scheduledTrigger do not affect eligibility). Forge confirmed eligibility on deploy of Forge app version 3.0.0 (app 1.1.0), of Forge app version 3.2.0 (app 1.2.0) and of the 4.x development deploy (app 1.3.0) on 2026-09-29. Verify with forge eligibility before each release.
  • E-mail: the app sends none and cannot (Forge has no mail API and the app has no egress). Assignees of reminder tasks are notified by Jira's own notification scheme.

9. Data residency

All stored data (the snapshot log, the policy, the project list and the reminder keys) is kept exclusively in persistent Forge-hosted storage. Atlassian's Forge data-residency documentation states that an app is eligible for PINNED status when it stores in-scope End-User Data exclusively in persistent Forge hosted storage, that such data "will be hosted in the admin's chosen location", and that if an admin moves the site to another location "all installed Forge apps using persistent Forge hosted storage will also be migrated there". So the log follows the customer's Jira site's region with no action from us. Export data read by the app comes from wherever the customer's Jira site is hosted and goes to wherever the user's device is.

10. Security practices (vendor)

  • Least privilege: one read scope, one write scope confined to a single optional feature, plus app storage for metadata; scope changes are treated as major versions and explained in the changelog (1.1.0 added storage:app; Forge major version 3.0.0. 1.2.0 added no scope; Forge version 3.2.0. 1.3.0 added write:jira-work for reminder tasks; Forge major version 4.x). The write path is a single function with a hard cap of 20 issues per run and duplicate protection.
  • Dependencies: 7 runtime packages (react, react-dom, @forge/bridge, @forge/api, @forge/resolver, @forge/kvs, fflate), all pinned in the lockfile and resolved from registry.npmjs.org; npm audit run before each release; none performs network I/O at runtime. Two transitive packages (iframe-resizer via @forge/bridge, and the build tool esbuild) run install scripts on the developer's machine at build time only.
  • Build: reproducible Vite build; forge deploy from a clean checkout; no CI service holds Atlassian credentials beyond the developer's own machine.
  • Testing: unit tests for the export engine, the resolver authorization, the policy check and the policy logic (101 passing after the 2026-09-30 review), including manifest hashing, part splitting, incremental JQL, HTML escaping and link filtering, CSV formula protection, filename sanitisation, verification against the manifest, policy validation, stale-project selection, the reminder issue fields and the duplicate-detection JQL.
  • Vulnerability reports: andre@figflows.com — we acknowledge within 2 business days and aim to fix confirmed issues in the app within 30 days. We do not take part in the paid Marketplace Security Bug Bounty Program; reports by e-mail are welcome and credited.
  • Incident response: because the app holds no product data (the log is metadata only), the realistic incidents are (a) a bug that makes an export incomplete or wrong, and (b) a compromised dependency. For (a) we publish a fix and a changelog note; for (b), and for any other security incident, we notify Atlassian within 48 hours as the Marketplace Partner Agreement requires, post a security advisory in the docs, and inform affected customers in coordination with Atlassian.
  • Certifications: none (SOC 2, ISO 27001 are not proportionate for a one-person vendor whose only stored data is metadata inside Atlassian). We answer CAIQ-Lite on request; most answers are "not applicable — no data stored outside Atlassian".

11. What the customer should still do

  • Decide who may run exports (project admin role).
  • Store exported ZIPs on encrypted disks or in an access-controlled archive.
  • Verify manifest.json hashes when the archive is used as evidence — with the Verify a snapshot tab or on the command line.
  • Keep incremental ZIPs together with the full snapshot they extend; an incremental part on its own is not a complete record.
  • Treat the HTML archive like the JSON: it is static and safe to open offline, but it contains the same personal data.
  • Treat exports as containing personal data of users named in issues; apply your retention policy to them.
  • Know that the snapshot log records when each export ran and, visible to Jira administrators only, who ran it (account id) and the JQL used; anyone who can browse the project sees its dates, mode and counts.
  • If you switch the snapshot policy on with a reminder project, choose a project whose members should see which projects are behind on snapshots: each reminder task names the project (key and name) and links to its export page. Anyone who can see the reminder project sees those tasks. Use the ignore list for projects that should not be checked.
  • The policy check works from the project list remembered when a Jira admin last opened the Coverage or Policy page. Open one of them after creating projects so the check knows about them.
